Usage Models

Composing an Aaron Node

Aaron provides a composable API. Start with a lightweight single-node service in 15 lines, or scale up to a resilient cluster member with gossip, telemetry, and an admin console. 

// Minimal Model: A lightweight node with embedded persistent storage
use aaron::{Context, Node, service_fn};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 1. Create the runtime execution container
    let node = Node::new("order-service")
        // 2. Register a supervised async microservice
        .with(service_fn("orders", |ctx: Context| async move {
            // Access isolated keyspace in the Fjall LSM engine
            let orders = ctx.store.keyspace("orders")?;

            // Disk write with WAL and ~6 microsecond latency
            orders.insert("order:1001", br#"{"customer":"alice","amount":99.50}"#)?;
            ctx.store.persist()?;

            // Sub-millisecond point lookup
            if let Some(payload) = orders.get("order:1001")? {
                println!("Order stored: {}", String::from_utf8_lossy(&payload));
            }
            Ok(())
        }));

    println!("Aaron Node active and supervising services.");
    node.run().await?;
    Ok(())
}
// Production Model: Distributed cluster node with SWIM gossip and Admin UI
use aaron::{
    admin::AdminService,
    membership::{MembershipConfig, MembershipEvent, MembershipService},
    tracing::TracingService,
    Context, Node, Uuid,
};
use std::time::Duration;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 1. Configure SWIM gossip protocol and O(1) failure detection
    let mem_cfg = MembershipConfig {
        bind_addr: "0.0.0.0:18100".to_string(),
        seeds: vec!["10.0.0.1:18100".to_string()], // Seed node for initial bootstrap
        cluster_id: Some(Uuid::random()),
        probe_interval: Duration::from_millis(400),
        probe_timeout: Duration::from_millis(150),
        suspect_timeout: Duration::from_millis(1200),
        indirect_ping_targets: 3,
        gossip_fanout: 3,
    };
    let (membership, handle) = MembershipService::pair_with_config(mem_cfg);

    // 2. Compose the node with observability, clustering, and Vue 3 Admin UI
    let node = Node::new("worker-01")
        .with(TracingService::new())                                // Dynamic log level reload
        .with(membership)                                          // SWIM protocol over QUIC transport
        .with(AdminService::new().with_membership_handle(handle)); // Embedded web console on port 28100

    // 3. React to cluster topology events in real time (internal EventHub)
    let mut sub = node.context().event_hub.subscribe::<MembershipEvent>().await;
    tokio::spawn(async move {
        while let Ok(event) = sub.recv().await {
            match event {
                MembershipEvent::MemberJoined { node_id, addr } => {
                    println!("Node {node_id} joined cluster via {addr}");
                }
                MembershipEvent::MemberSuspect { node_id } => {
                    println!("Node {node_id} suspected faulty. Dispatching indirect probes...");
                }
                MembershipEvent::MemberDead { node_id } => {
                    println!("Node {node_id} confirmed DEAD by the mesh.");
                }
            }
        }
    });

    println!("Node active. Management console available at http://localhost:28100");
    node.run().await?;
    Ok(())
}

Opinionated Architecture

Anatomy of an Aaron Node

Instead of relying on sprawling external infrastructure, each Aaron node is a self-contained runtime unit providing the fundamental building blocks of a modern distributed system.

Aaron Node Instance (Single Rust Process)
Identity: Cluster UUID + Node ID + Incarnation

Service Supervisor

Manages the lifecycle of async actors and microservices via Tokio. Injects shared Context and orchestrates graceful shutdown via CancellationToken.

Tokio Supervision

Fjall LSM Storage Engine

Embedded disk persistence with Write-Ahead Logging (WAL), logical keyspace partitioning, and write latency in the ~6 microsecond range.

Disk-backed LSM Tree

QUIC Multi-Stream Fabric

Secure UDP transport with mutual TLS 1.3 and auto-generated certificates. Stream multiplexing eliminates Head-of-Line blocking across concurrent services.

Quinn / Rustls TLS 1.3

SWIM Gossip Membership

Decentralized O(1) node discovery and health monitoring. Employs direct and indirect (ping-req) probing with Alive → Suspect → Dead states and incarnation refutation.

O(1) Bounded Probing

Internal EventHub Bus

In-memory async pub/sub bus for local decoupling. Allows services to subscribe to topology transitions, partition warnings, and telemetry events.

Type-safe Event Bus

Admin & Observability

Embedded REST management API and Vue 3 web dashboard packaged into the binary via rust-embed. Dynamic log level reload without process restarts.

Single-binary SPA UI
Resilience & State Transitions

Cluster Node Lifecycle

How nodes join the mesh, converge topology state, detect network partitions, and autonomously self-heal without manual intervention.

01
Bootstrap & Initial Discovery Initialization

The node allocates its QUIC port, initializes local Fjall LSM storage, and assigns its unique Uuid. If seed addresses are configured, it performs handshake probes against the seed; otherwise, it operates as the initial seed for subsequent peers.

02
SWIM Gossip Convergence O(log N) Dissemination

The gossip engine propagates the new node across the mesh in bounded random steps. Each node maintains an ordered local membership table and disseminates updates probabilistically via QUIC datagrams.

03
Failure Detection: Direct & Indirect (Ping-Req) Suspect State

At configured probe intervals (e.g. 400ms), a node pings a random peer. Upon probe timeout (150ms), it recruits 3 neighboring peers to execute indirect ping-req probes. If unanswered, the target enters the Suspect state with a decay timer.

04
Dead Declaration or Incarnation Self-Healing Self-Healing

If the suspicion timer expires without refutation, the node is declared Dead and evicted from active routing. However, if the node was temporarily delayed or crashed and restarted, it refutes the suspicion by incrementing its incarnation counter, immediately restoring Alive status without cluster restarts.

05
Graceful Drain & Shutdown Graceful Drain

During planned termination (SIGTERM / CancellationToken), async services drain in-flight requests, Fjall LSM tables flush pending commits to disk, and the node dispatches departure notifications to peers to prevent false suspect alarms.
